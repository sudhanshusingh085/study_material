00 Foundations

00What is EKS, and why does it exist?

Kubernetes is software that runs your applications across a group of machines, restarting them when they crash, spreading them out for load, and rolling out updates without downtime. The problem: Kubernetes itself is made of several moving parts — a database (etcd), an API server, a scheduler, controllers — and someone has to install, patch, secure, and keep all of that alive 24/7. That "someone" is normally you.

EKS (Elastic Kubernetes Service) is AWS running that hard part for you. AWS hosts and operates the Kubernetes control plane — the brain of the cluster — across multiple data centers, patches it, backs it up, and makes it highly available. You bring the worker machines (or let AWS manage those too), and you focus on running your applications instead of babysitting cluster infrastructure.

Mental model

Think of Kubernetes as an operating system for a data center, and EKS as AWS selling you that operating system already installed, patched, and monitored — you just plug in computers (nodes) and start running programs (pods) on it.

Why not just run Kubernetes yourself on EC2?

You can — it's called "self-managed Kubernetes," and tools like kubeadm exist for it. But you'd be responsible for: keeping 3+ control plane nodes alive across failure zones, upgrading Kubernetes versions without breaking your API, securing etcd (which holds every secret in your cluster), and scaling the control plane as load grows. EKS removes all of that. You pay AWS roughly $0.10/hour per cluster for the control plane, and in exchange you never SSH into a control plane node — because there isn't one you can access.

Where EKS sits among your options

OptionWhat you manageBest for
EC2 + kubeadmEverything — control plane and workersLearning internals, extreme customization
EKS with EC2 nodesWorker nodes onlyMost production workloads — this guide's focus
EKS with FargateNothing — not even nodesSimplicity, spiky/unpredictable workloads
ECSNothing, but it's not KubernetesAWS-only shops who don't need K8s portability
Why this matters to you

Skills learned on EKS transfer to any Kubernetes — GKE, AKS, on-prem — because the API and concepts are identical. Only the "how the control plane is hosted" part is AWS-specific. This is the biggest reason companies pick EKS over ECS: it avoids lock-in.

01 Foundations

01Kubernetes primer — the vocabulary you need first

Before touching AWS, you need five words. Everything else in Kubernetes is built from these.

Pod

The smallest deployable unit. One or more containers that always run together on the same machine, sharing network and storage.

Node

A machine (virtual or physical) that runs pods. In EKS, a node is an EC2 instance or a Fargate slot.

Deployment

A blueprint that tells Kubernetes "keep N copies of this pod running, and here's how to roll out changes."

Service

A stable network address that routes traffic to whichever pods are currently alive, even as pods are replaced.

Namespace

A virtual wall inside one cluster — a way to separate teams or environments (dev/staging/prod) without separate clusters.

etcd

The database that stores the entire cluster's state — every pod, service, and config. In EKS, AWS runs and secures this for you.

The declarative model — the single most important idea

You never tell Kubernetes "start a container." You describe the desired state in a YAML file — "I want 3 copies of this app running" — and submit it to the API server. A background loop called a controller continuously compares desired state to actual state and takes action to close the gap. Kill a pod manually, and within seconds a controller notices one is missing and starts a replacement. This self-healing loop is the core mechanic behind everything Kubernetes does.

Why EKS needs this context

Every AWS-specific thing you'll learn from here on — IAM roles, load balancers, storage classes — is just Kubernetes' declarative model calling out to AWS APIs to fulfill desired state. An Ingress object doesn't create a load balancer itself; a controller watches for Ingress objects and calls the AWS API on your behalf.

02 Foundations

02Cluster architecture — the full map

This is the diagram we'll keep returning to. It shows every layer of an EKS cluster: the AWS-managed control plane, your VPC, the subnets that separate public and private resources, and where your actual application pods run. Study this once now — every later section builds one piece of it.

Fig. 1 — An EKS cluster spans an AWS-managed control plane and your own VPC. You never see or touch the control plane's servers directly.

Reading this diagram

  • Control plane (top, amber border): lives in an AWS-owned VPC you can't see. You interact with it only through the Kubernetes API — never SSH.
  • Public subnets: host things that need direct internet exposure — NAT Gateways and Load Balancers. Your actual application pods should not run here.
  • Private subnets: host your worker nodes and pods. They reach the internet outbound only through the NAT Gateway, and receive inbound traffic only through the Load Balancer.
  • Two compute choices: Managed Node Groups (you pick EC2 instance types, AWS handles lifecycle) or Fargate (no EC2 visible at all — you pay per pod).
Common beginner mistake

Putting worker nodes in public subnets "to make things simpler." This exposes every node directly to the internet and is flagged by every AWS security review. Always run nodes in private subnets — this guide does that from the start.

03 Foundations

03Under the hood — how AWS actually runs this

Everything so far described EKS from the outside. This section opens the box: what physically happens when you create a cluster, how the control plane achieves high availability, how VPC networking is implemented at the packet level, and how IAM authentication actually works. You don't need this to use EKS, but it's what separates "I can run commands" from "I know why they work."

The control plane, internally

When you run eksctl create cluster, AWS doesn't spin up one server for your control plane — it provisions a dedicated, per-cluster set of resources inside an AWS-owned VPC that no customer can see or access directly:

  • Multiple API server instances behind a Network Load Balancer, spread across at least 3 Availability Zones. This is why the control plane survives an entire AZ outage.
  • A dedicated etcd cluster (typically 3 or 5 nodes for quorum), also multi-AZ, storing every object in your cluster as key-value pairs. etcd uses the Raft consensus algorithm — a write only succeeds once a majority of etcd nodes agree, which is why an odd number of nodes is used.
  • Scheduler and controller-manager processes, running in an active/standby configuration with leader election, so exactly one instance is making decisions at any moment even though multiple are running.

AWS runs this per-customer, per-cluster — your control plane is not multi-tenant with anyone else's. This isolation is why EKS clusters cost a flat hourly fee: you're paying for genuinely dedicated (if AWS-managed) infrastructure, not a shared pool.

Why you can't SSH into it

There's no meaningful "into" — the control plane's compute is inside AWS's own service account/VPC, invisible and inaccessible by design, similar to how you can't SSH into the server running S3. The only interface AWS exposes is the Kubernetes API itself.

How the API server authenticates you, step by step

Every kubectl command actually makes an HTTPS call to the API server. Here's the exact sequence for an EKS cluster specifically:

  1. kubectl reads your kubeconfig, which (for EKS) doesn't store a static token — it stores a command to generate one, via the aws eks get-token mechanism.
  2. That command uses your local AWS credentials to create a specially crafted, pre-signed STS (Security Token Service) URL — essentially an AWS API call that proves your IAM identity, valid for 60 seconds, without ever transmitting your secret key itself.
  3. This signed token is sent to the API server as a bearer token.
  4. The API server calls a component called aws-iam-authenticator (built into EKS), which validates the token against AWS STS and extracts your IAM identity (user or role ARN).
  5. That IAM identity is looked up in the aws-auth ConfigMap (Section 08) to determine your Kubernetes username and groups.
  6. Only now does standard Kubernetes RBAC evaluate whether that username/group can perform the requested action.

This is why a brand new IAM user, even an Administrator, gets a "Unauthorized" error against a cluster they aren't mapped into — steps 1-4 succeed (AWS confirms who they are), but step 5 finds no matching entry.

VPC networking, at the packet level

The detail that surprises most newcomers: pods on EKS get real IP addresses from your VPC's actual CIDR range — not an overlay/NAT'd address like most other Kubernetes distributions use. This is the job of the VPC CNI plugin.

Fig. 3 — The VPC CNI pre-allocates "warm" IPs onto each node's Elastic Network Interfaces so new pods start instantly instead of waiting on an IP request.

The practical consequence: your VPC's IP address space directly limits how many pods you can run. A /24 subnet (256 addresses) fills up fast once you account for one IP per pod, per ENI overhead, and reserved AWS addresses. This is the single most common scaling wall production EKS teams hit — solved by either using larger CIDR blocks, enabling custom networking (a secondary, larger CIDR just for pods), or switching to prefix delegation mode, where each ENI is assigned an address prefix instead of individual IPs, multiplying pod density per node roughly 16x.

Plan your CIDR before you launch, not after

Resizing a VPC's CIDR after a cluster is live and full of resources is painful. For any cluster expected to grow, use at minimum a /20 per subnet, and consider enabling prefix delegation from day one.

How IAM roles actually authorize an AWS API call

IAM has no concept of "identity" the way a username/password does. Under the hood, every single AWS API call — whether from your CLI, a pod via IRSA, or the EKS control plane itself — is a request signed with SigV4 (Signature Version 4): a cryptographic signature computed from your credentials, the request contents, and a timestamp. AWS recomputes that same signature server-side using its own record of your secret key; if they match, the request is authentic and unmodified in transit.

This is why IRSA (Section 08) is secure without ever storing a secret key in your cluster: the pod obtains a short-lived temporary credential (access key + secret + session token, valid ~1 hour) from STS, and that temporary credential is what gets used to compute the SigV4 signature — not a permanent key. When it expires, the pod transparently fetches a new one.

The one-sentence version

AWS internals reduce to three durable ideas: the control plane is real, dedicated, multi-AZ infrastructure you simply can't reach directly; every authenticated action — human or pod — resolves to a signed, time-limited proof of identity; and pod networking is not virtual, it's genuinely your VPC's address space, which is why capacity planning for IPs matters as much as capacity planning for CPU.

05 Setup

05VPC & networking — the part everyone underestimates

Networking mistakes are the #1 source of "why can't my pod reach the internet" and "why is my load balancer stuck pending" issues. Understanding this now saves hours later.

Core vocabulary

VPC

Your own private, isolated network inside AWS. Everything you create lives inside one.

Subnet

A slice of your VPC's IP range, tied to one Availability Zone. You split into public and private subnets.

Availability Zone (AZ)

A physically separate data center within a region. EKS requires subnets across at least 2 AZs for high availability.

Route Table

Rules that decide where traffic from a subnet goes. This is what makes a subnet "public" or "private."

Internet Gateway (IGW)

The door between your VPC and the internet. Attached at the VPC level, used by public subnets.

NAT Gateway

Lets private subnets reach the internet outbound (e.g. to pull a container image) without allowing inbound connections.

What makes a subnet "public" vs "private"?

There's no checkbox — it's purely defined by the route table. A subnet is public if its route table sends 0.0.0.0/0 traffic to an Internet Gateway. It's private if that traffic instead goes to a NAT Gateway (or nowhere at all).

# Public subnet route table
Destination: 10.0.0.0/16   → local
Destination: 0.0.0.0/0     → igw-0123abcd     ← this line makes it public

# Private subnet route table
Destination: 10.0.0.0/16   → local
Destination: 0.0.0.0/0     → nat-0456efgh     ← outbound only, this makes it private

EKS-specific subnet tags

EKS and its controllers (like the load balancer controller you'll install later) discover subnets by AWS resource tags, not by asking you. If these tags are missing, your Ingress will silently fail to provision a load balancer — a very common point of confusion.

# Public subnets need:
kubernetes.io/role/elb                    = 1
kubernetes.io/cluster/<your-cluster-name> = shared

# Private subnets need:
kubernetes.io/role/internal-elb           = 1
kubernetes.io/cluster/<your-cluster-name> = shared
Good news

If you let eksctl create your VPC (next section), it applies all of these tags automatically. You only need to hand-manage tags if you brought your own pre-existing VPC.

06 Setup

06Creating your first cluster

Two ways to do this: the fast way (eksctl, one command) and the "understand every piece" way (AWS Console, click by click). Do the fast way first to get a working cluster, then read what it did.

The fast way

eksctl create cluster \
  --name my-first-cluster \
  --region us-east-1 \
  --version 1.30 \
  --nodegroup-name standard-workers \
  --node-type t3.medium \
  --nodes 2 \
  --nodes-min 2 \
  --nodes-max 4 \
  --managed

This single command, over roughly 15–20 minutes:

  1. Creates a new VPC with public and private subnets across 2 AZs, correctly tagged
  2. Creates the EKS control plane (the AWS-managed piece from Fig. 1)
  3. Creates an IAM role for your nodes with the correct permissions
  4. Launches a Managed Node Group of 2 EC2 instances in the private subnets
  5. Wires up your local kubectl to talk to the new cluster
This costs real money

The control plane is ~$0.10/hour (~$73/month) regardless of usage, plus EC2 costs for your nodes. Run eksctl delete cluster --name my-first-cluster when you're done experimenting to avoid ongoing charges.

Verify it worked

kubectl get nodes
# NAME                          STATUS   ROLES    AGE   VERSION
# ip-192-168-45-12.ec2.internal Ready    <none>   4m    v1.30.0
# ip-192-168-78-93.ec2.internal Ready    <none>   4m    v1.30.0

kubectl get svc
# NAME         TYPE        CLUSTER-IP   PORT(S)   AGE
# kubernetes   ClusterIP   10.100.0.1   443/TCP   10m

If kubectl get nodes shows your two nodes as Ready, your control plane and worker nodes are talking to each other correctly — you have a real, working Kubernetes cluster running on AWS.

What eksctl actually generated (the config-file way)

For real projects, don't run one giant CLI command — write a YAML config file so your cluster definition is version-controlled and repeatable.

# cluster.yaml
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: my-first-cluster
  region: us-east-1
  version: "1.30"

managedNodeGroups:
  - name: standard-workers
    instanceType: t3.medium
    desiredCapacity: 2
    minSize: 2
    maxSize: 4
    privateNetworking: true
eksctl create cluster -f cluster.yaml

07Node groups — managed vs. self-managed

A node group is simply a set of EC2 instances that all join your cluster as worker nodes. There are two flavors.

Managed Node GroupSelf-managed Node Group
AMI updatesOne-click via console/CLIYou build and rotate AMIs yourself
Node draining on updateAutomatic, respects PodDisruptionBudgetsYou script it

Custom AMIs / bootstrappingLimitedFull control

Scaling a node group

eksctl scale nodegroup \
  --cluster my-first-cluster \
  --name standard-workers \
  --nodes 4

Adding a second node group (e.g. for a different workload type)

A very common real-world pattern: one node group of cheap instances for general workloads, another of larger/GPU instances for specific jobs. Kubernetes uses labels and taints to steer pods to the right group.

eksctl create nodegroup \
  --cluster my-first-cluster \
  --name gpu-workers \
  --node-type g4dn.xlarge \
  --nodes 1 \
  --node-labels "workload=gpu"
# In your pod spec, request that label:
nodeSelector:
  workload: gpu
08 Compute

08Fargate — running pods with zero visible servers

With Fargate, there is no EC2 instance for you to see, patch, or scale. You define a Fargate profile that says "any pod landing in this namespace runs on Fargate," and AWS launches a right-sized micro-VM per pod automatically.

Trade-off

Fargate is simpler and bills per-pod-second, but has real constraints: no DaemonSets, no privileged containers, slower pod startup (30–60s vs. seconds on EC2), and it's typically more expensive at sustained high utilization than reserved EC2 capacity.

Creating a Fargate profile

eksctl create fargateprofile \
  --cluster my-first-cluster \
  --name fp-default \
  --namespace fargate-apps

Any pod you now create in the fargate-apps namespace automatically runs on Fargate — no node group, no EC2, nothing else to configure.

When to reach for Fargate

  • Batch or scheduled jobs with unpredictable, spiky demand
  • Small teams who want zero node patching responsibility
  • Multi-tenant clusters where strict pod-level isolation matters

For steady, predictable, high-volume workloads, Managed Node Groups (especially with Spot instances) are usually cheaper — see the cost section later.

09 Identity & Access

09IAM, RBAC & IRSA — the most confusing part, explained clearly

EKS has two separate permission systems that beginners constantly conflate:

AWS IAM

Controls who can call AWS APIs — create a cluster, describe a node group, read an S3 bucket. Lives entirely outside Kubernetes.

Kubernetes RBAC

Controls who can do what inside the cluster — create a pod, view a secret, delete a deployment. Lives entirely inside Kubernetes and knows nothing about AWS.

The gap this creates

Being an AWS Administrator does NOT automatically let you run kubectl commands against a cluster. IAM authenticates you as a user, but RBAC decides what that user is allowed to do inside Kubernetes. The two must be linked explicitly.

Linking IAM to Kubernetes RBAC: aws-auth

The bridge is a ConfigMap called aws-auth living in the kube-system namespace. It maps IAM users/roles to Kubernetes usernames and groups.

apiVersion: v1
kind: ConfigMap
metadata:
  name: aws-auth
  namespace: kube-system
data:
  mapRoles: |
    - rolearn: arn:aws:iam::123456789012:role/eks-node-role
      username: system:node:{{EC2PrivateDNSName}}
      groups:
        - system:bootstrappers
        - system:nodes
  mapUsers: |
    - userarn: arn:aws:iam::123456789012:user/priya
      username: priya
      groups:
        - system:masters   # full admin inside the cluster

The other direction: letting pods call AWS — IRSA

Now flip it: your application pod needs to read from an S3 bucket. How does a pod safely get AWS credentials without you hardcoding an access key into your container (never do this)?

The answer is IRSA — IAM Roles for Service Accounts. EKS clusters have an OIDC (OpenID Connect) identity provider built in. This lets a Kubernetes ServiceAccount assume a real IAM role directly, with temporary, auto-rotating credentials, and zero secrets stored anywhere.

Fig. 2 — IRSA lets a single pod assume a narrowly-scoped IAM role, with no long-lived secret ever stored in the cluster.
# 1. Create an IAM role trusted by your cluster's OIDC provider, then annotate a ServiceAccount:
apiVersion: v1
kind: ServiceAccount
metadata:
  name: s3-reader
  namespace: default
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/s3-read-role
# 2. Reference that ServiceAccount from your pod/deployment:
spec:
  serviceAccountName: s3-reader
  containers:
    - name: app
      image: my-app:latest
Rule of thumb

aws-auth answers "which humans/CI systems can run kubectl against my cluster." IRSA answers "which pods can call which AWS APIs." Never give a pod broad IAM permissions "just in case" — scope every IRSA role to exactly what that one workload needs.

10 Running Workloads

10Deployments & Services — actually running your app

With a cluster ready, here's the minimum you need to get a real application running and reachable.

A Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: hello-app
  template:
    metadata:
      labels:
        app: hello-app
    spec:
      containers:
        - name: hello-app
          image: nginxdemos/hello:latest
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "250m"
              memory: "256Mi"
Never skip resources.requests/limits

Without these, the scheduler can't reason about bin-packing, one runaway pod can starve every other pod on the node, and autoscaling (Section 12) has nothing to calculate against. Set these on every workload, always.

A Service

Pods are ephemeral — they get new IPs every time they restart. A Service gives your app a stable address that automatically tracks whichever pods are currently healthy.

apiVersion: v1
kind: Service
metadata:
  name: hello-app-svc
spec:
  selector:
    app: hello-app   # matches the Deployment's pod labels
  ports:
    - port: 80
      targetPort: 80
  type: ClusterIP  # internal-only by default
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl get pods -w      # watch pods come up
kubectl get deployments  # check rollout status

Service types, and when to use each

TypeReachable fromUse case
ClusterIPInside the cluster onlyInternal microservice-to-microservice traffic (default, most common)
NodePortAny node's IP, on a fixed portRarely used directly on EKS — mostly a building block
LoadBalancerThe public internetProvisions a real AWS ELB — simple but one ELB per Service gets expensive at scale

For exposing many services to the internet cost-effectively, you generally want a single shared load balancer routing by hostname/path — that's what Ingress is for, next.

11 Running Workloads

11Ingress & the AWS Load Balancer Controller

An Ingress object describes URL-based routing rules ("/api goes to the api service, /web goes to the web service") — but by itself, Kubernetes doesn't know how to turn that into real infrastructure on AWS. You need a controller watching for Ingress objects and translating them into an actual Application Load Balancer (ALB).

Install the AWS Load Balancer Controller

# 1. Create the IAM policy it needs, then an IRSA-backed service account
eksctl create iamserviceaccount \
  --cluster my-first-cluster \
  --namespace kube-system \
  --name aws-load-balancer-controller \
  --attach-policy-arn arn:aws:iam::123456789012:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve

# 2. Install the controller itself via Helm
helm repo add eks https://aws.github.io/eks-charts
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=my-first-cluster \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller

Define an Ingress

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: hello-app-ingress
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: hello-app-svc
                port:
                  number: 80

Apply it, wait a couple of minutes, then check kubectl get ingress — the ADDRESS column fills in with a real ALB DNS name once provisioning completes.

If ADDRESS stays empty

This is almost always the subnet tagging issue from Section 04 — the controller can't find subnets tagged kubernetes.io/role/elb. Check kubectl logs -n kube-system deployment/aws-load-balancer-controller for the exact reason.

12Storage — persisting data beyond a pod's life

Pods are disposable — anything written to a container's own filesystem vanishes when it restarts. For anything that needs to survive, EKS integrates with two AWS storage services via the Container Storage Interface (CSI).

DriverBacking serviceAccess modeUse case
EBS CSIElastic Block StoreOne pod at a time (ReadWriteOnce)Databases, single-writer workloads
EFS CSIElastic File SystemMany pods at once (ReadWriteMany)Shared config, multiple pods reading/writing the same files

Install the EBS CSI driver

eksctl create iamserviceaccount \
  --cluster my-first-cluster \
  --namespace kube-system \
  --name ebs-csi-controller-sa \
  --attach-policy-arn arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy \
  --approve

eksctl create addon --cluster my-first-cluster --name aws-ebs-csi-driver

Claiming storage for a pod

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-storage
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: gp3
  resources:
    requests:
      storage: 20Gi

Reference db-storage as a volume in your pod spec, and EKS provisions a real EBS volume on demand, attaching and mounting it wherever the pod is scheduled.

13 Operating at Scale

13Autoscaling — three layers, not one

"Autoscaling" on EKS actually means three independent systems, each answering a different question.

HPA (Horizontal Pod Autoscaler)

"Do I need more copies of my app?" Watches CPU/memory or custom metrics, adjusts replica count.

Cluster Autoscaler / Karpenter

"Do I need more nodes?" Watches for unschedulable pods and adds/removes EC2 capacity.

VPA (Vertical Pod Autoscaler)

"Is each pod sized correctly?" Recommends or auto-adjusts CPU/memory requests per pod.

HPA — scale replicas by load

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hello-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hello-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

This requires the Metrics Server add-on: eksctl create addon --cluster my-first-cluster --name metrics-server

Cluster Autoscaler vs. Karpenter

When HPA needs more replicas but there's no room on existing nodes, pods sit Pending until something adds node capacity.

Cluster AutoscalerKarpenter
ApproachScales predefined Auto Scaling Groups up/downProvisions right-sized nodes directly, no ASG needed
SpeedSlower — bound by ASG scaling logicFaster — picks optimal instance type/AZ in real time
MaturityOlder, battle-tested, K8s-project standardNewer, AWS-built, increasingly the recommended default
RecommendationFine for simple, single-instance-type setupsPreferred for mixed instance types, Spot usage, cost optimization
Karpenter in one command

AWS now ships a Karpenter Helm chart with sane EKS defaults — for new clusters in 2025+, start with Karpenter rather than Cluster Autoscaler unless you have a specific reason not to.

14Observability, in depth

You cannot operate a cluster you can't see into. This section goes past "install an add-on" and into how each pillar actually works, how to run a real Prometheus/Grafana stack, how tracing is wired in, and how to alert on the metrics that matter.

PillarQuestion it answersCommon EKS tooling

14.1 — How metrics actually flow, under the hood

It helps to see the full pipeline rather than treat "metrics" as a black box.

Fig. 4 — Metrics are pulled (scraped), not pushed. Each hop is a separate, swappable component.

Two implementation details that matter in practice: Prometheus works by scraping — it polls a known /metrics HTTP endpoint on each target on a schedule (commonly every 15–30s) — rather than apps pushing data out. And kubectl top / HPA don't talk to Prometheus at all; they depend on a separate, much simpler Metrics Server that only holds a few minutes of in-memory CPU/memory data. Prometheus is for historical analysis and alerting; Metrics Server is purely for real-time autoscaling decisions. Confusing the two is a common mistake — installing Prometheus does not make HPA work; you still need Metrics Server.

14.2 — Setting up Amazon Managed Prometheus + Grafana

Running your own Prometheus server means you now have to scale, back up, and secure yet another stateful service. Amazon Managed Prometheus (AMP) and Amazon Managed Grafana remove that operational burden while keeping the same open-source query language (PromQL) and dashboards you already know.

# 1. Create an AMP workspace (the managed, durable metrics database)
aws amp create-workspace --alias eks-prod-metrics

# 2. Note the resulting workspace ARN and remoteWriteUrl from the output, then
#    give your cluster's collector permission to write to it via IRSA:
eksctl create iamserviceaccount \
  --cluster my-first-cluster \
  --namespace kube-system \
  --name amp-iamproxy-ingest-service-account \
  --attach-policy-arn arn:aws:iam::aws:policy/AmazonPrometheusRemoteWriteAccess \
  --approve

# 3. Install the ADOT (AWS Distro for OpenTelemetry) Collector to scrape
#    cluster metrics and remote_write them into AMP
helm repo add aws-observability https://aws-observability.github.io/aws-otel-helm-charts
helm install adot-collector aws-observability/adot-exporter-for-eks-on-ec2 \
  -n kube-system \
  --set awsRegion=us-east-1

Then connect Grafana as the visualization layer on top:

# Create an Amazon Managed Grafana workspace (console or CLI), then add
# your AMP workspace as a data source inside the Grafana UI — no YAML needed.
aws grafana create-workspace \
  --workspace-name eks-dashboards \
  --account-access-type CURRENT_ACCOUNT \
  --authentication-providers AWS_SSO \
  --permission-type SERVICE_MANAGED
Fastest path if you just want dashboards today

Skip AMP/Grafana entirely and run eksctl create addon --name amazon-cloudwatch-observability — it installs the CloudWatch agent and Fluent Bit as DaemonSets automatically and gives you prebuilt Container Insights dashboards in the AWS Console within minutes. Reach for the Prometheus/Grafana path when you need PromQL, existing Grafana dashboards, or multi-cluster/multi-cloud views.

14.3 — Logs: how they get from a container to somewhere queryable

By default, anything your application writes to stdout/stderr is captured by the container runtime and stored briefly on the node's local disk — it disappears the moment the node is replaced. To persist logs, you run a log shipper as a DaemonSet (one copy per node) that tails those files and forwards them onward.

# Fluent Bit ships as part of the CloudWatch Observability add-on already
# installed above. To confirm it's running:
kubectl get daemonset -n amazon-cloudwatch

# Query shipped logs directly from the CLI with CloudWatch Logs Insights:
aws logs start-query \
  --log-group-name /aws/containerinsights/my-first-cluster/application \
  --start-time $(date -d '-1 hour' +%s) \
  --end-time $(date +%s) \
  --query-string 'fields @timestamp, @message | filter @message like /ERROR/'

14.4 — Distributed tracing with X-Ray

Metrics tell you that latency spiked; traces tell you where — which of your 12 microservices a slow request actually spent its time in. Tracing requires your application to be instrumented (via an SDK or auto-instrumentation agent) to emit trace spans, which are then collected and stitched together by trace ID.

# Deploy the X-Ray daemon as a DaemonSet so it's available on every node
# to receive trace data over UDP from your app's X-Ray SDK
kubectl apply -f https://raw.githubusercontent.com/aws-samples/aws-xray-kubernetes/master/xray-k8s-daemonset.yaml

# Your application code sends spans to it, e.g. in Node.js:
# const AWSXRay = require('aws-xray-sdk');
# app.use(AWSXRay.express.openSegment('my-app'));

Prefer vendor neutrality? Run an OpenTelemetry Collector instead — a single agent that can receive traces, metrics, and logs, and export to X-Ray, Jaeger, Tempo, or any combination simultaneously, so switching backends later doesn't mean re-instrumenting every application.

14.5 — Alerting: turning metrics into pages

A dashboard nobody is watching at 3am doesn't help. Alerting rules evaluate metrics continuously and fire notifications when thresholds are breached.

# A PromQL alerting rule, evaluated by Prometheus/AMP's rule engine
groups:
  - name: node-health
    rules:
      - alert: NodeMemoryPressure
        expr: node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes < 0.10
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Node {{ $labels.instance }} below 10% free memory"

These rules are typically evaluated by Amazon Managed Service for Prometheus's rule engine (or a self-run Alertmanager), which then routes firing alerts to Slack, PagerDuty, or email based on severity labels.

What to actually monitor first

  • Node pressure: memory/disk/PID pressure — a node under pressure starts evicting pods unpredictably
  • Pod restart counts: a sudden spike almost always means a bad deploy or a dependency outage
  • API server latency: if the control plane itself slows down, everything downstream degrades
  • Ingress/ALB 5xx rate and target response time: your actual user-facing health signal
  • Pending pods: a persistent backlog means your autoscaler isn't keeping up with demand

Everyday debugging commands

kubectl logs <pod-name>                    # see what a container printed
kubectl logs <pod-name> --previous          # logs from before a crash/restart
kubectl describe pod <pod-name>             # events, scheduling reasons, failures
kubectl top pods                            # live CPU/memory usage (needs metrics-server)
kubectl get events --sort-by='.lastTimestamp'  # cluster-wide recent events

15Security hardening — the non-negotiables

A short checklist covering the highest-impact, most commonly-missed security controls on real EKS clusters.

  • Private API endpoint where possible. By default the Kubernetes API server is reachable from the public internet (secured by IAM/RBAC, but still exposed). For production, restrict it: eksctl utils update-cluster-endpoints --cluster my-first-cluster --private-access=true --public-access=false
  • Least-privilege IRSA roles. Never attach AdministratorAccess to a pod's role. Scope to exact actions and resource ARNs needed.
  • Enable envelope encryption for Secrets. By default, Kubernetes Secrets are only base64-encoded in etcd, not encrypted. Enable KMS envelope encryption at cluster creation.
  • Network Policies. By default, every pod can talk to every other pod. Use Kubernetes NetworkPolicy objects (enforced by the VPC CNI or Calico) to restrict this to only necessary traffic.
  • Scan container images. Use Amazon ECR's built-in scanning or a tool like Trivy in CI to catch known CVEs before deployment.
  • Keep the control plane version current. AWS supports a rolling window of Kubernetes versions; unsupported versions stop receiving security patches.
  • Run as non-root. Set securityContext.runAsNonRoot: true on every pod spec you can.
# Example: enabling secrets encryption at cluster creation (cluster.yaml)
secretsEncryption:
  keyARN: arn:aws:kms:us-east-1:123456789012:key/abcd-1234

16Cost optimization

EKS bills are almost always dominated by EC2, not the control plane. Where to look first.

LeverTypical savingsTrade-off
Spot instances for stateless workloadsUp to 70–90% vs. on-demandNodes can be reclaimed with 2-min warning — design for interruption
Right-sizing requests/limitsHighly variable, often 20–40%Requires monitoring actual usage, not guessing
Karpenter consolidation10–30%Bin-packs pods onto fewer, better-fit nodes automatically
Fargate for spiky/low-trafficAvoids paying for idle nodesCosts more per-unit at sustained high load
Single NAT Gateway (dev only)~$32/month per extra NAT Gateway avoidedLoses AZ-level redundancy — never do this in production
Mixing Spot and On-Demand safely

A common, safe pattern: run baseline capacity on On-Demand or Reserved nodes, and let Karpenter burst extra capacity onto Spot for stateless, horizontally-scaled workloads only. Never put a database's only replica on Spot.

Everything above, assembled into one sequence. Run this top to bottom to go from nothing to a real app on the internet.
